プロジェクトに小さな機能を追加しました。より大きな変更には、さらに堅牢なプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って作業できるように設計されており、適切なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスを実践します。Issue を起点に新機能を作成し、コードが有効で機能が期待どおりに動作することを確かめ、最終的にプロジェクトへ正常にマージします。

> [!NOTE]
> 機能の作業を続ける間、同じセッションを使用します。通常はファイルの種類ごとに異なるセッションや PR を使いますが、ここでは主な概念に集中できるよう簡略化しています。

このレッスンでは、次のことを行います。

- GitHub Issue から新しいエージェント セッションを始めます。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザー キャンバスで機能を手動検証します。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズして、MCP による検証を追加し、QA エージェントを作成して、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、訪問者がゲームをカテゴリとパブリッシャーで絞り込める必要があります。バックログの Issue には機能が記載されていますが、カテゴリを組み合わせる方法など、コーディング前に合意すべき詳細があります。Plan モードで決定し、範囲を限定した実装を Autopilot に任せます。

## 背景

AI コーディング エージェントを開発フローに導入しても、基本は変わりません。むしろ、基本はさらに重要になります。多くの開発者は、次のような流れで作業します。

1. 必要な作業の詳細を記述した Issue を開きます。
2. 実装する内容を計画します。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードのレビューと継続的インテグレーションが成功したら、マージします。

> [!NOTE]
> チームや Organization によって詳細は異なりますが、ほとんどの場合は上記の流れを調整したものになります。

この標準的な方法を守ることで、AI が生成したコードが要件を満たし、手書きのコードと同じ検証プロセスを通るようにできます。

## セッション モード

**セッション モード**は、エージェントにどの程度の自律性を与えるかを制御します。プロンプト フィールド下のドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントと一緒に作業します。エージェントは変更を提案し、続行前に入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントは入力を待たずに、コードの作成、テストの実行、反復を自律的に行います。

まず Plan モードで開始し、計画をレビューしてから、Autopilot で実装します。

## Issue からセッションを開始する

開始前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys リポジトリ フォルダーを選び、リポジトリ上部のナビゲーションで **Issues** を選択します。既存の **Allow users to filter games by category and publisher** Issue を開きます。テンプレートに用意されているため、新しい Issue を作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

   ![GitHub Copilot app の Issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モード選択で **Plan** を選びます。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` の実行を依頼します。ターミナルでは動作するのにセッションから使えない場合は、アプリの PATH またはバージョン管理ツールの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行し、エージェントがコマンドを見つけられないという理由だけで npm を再インストールしないでください。

## フィルタリング機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチをレビューできます。Issue から開始したため、Copilot は機能要求をすでにコンテキストとして持っています。次を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、Issue の受け入れ条件に照らして計画を確認します。カテゴリとパブリッシャーのフィルタリング、アクセシブルなコントロール、データ アクセスの変更、テストが含まれていることを確かめます。複数カテゴリの組み合わせ方や、一致するゲームがない場合の動作など、不明確な点について話し合います。

計画には、プロジェクト既存のツールを使った lint、単体テスト、E2E テスト、型チェックが必要です。フィルタリングの実装とテストに範囲を絞り、品質ワークフローが終わってから PR を作成します。承認前に計画の修正を依頼し、後から検証するために Issue の URL と合意事項を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan** または使用中のバージョンで同等のオプションを選択します。承認によってモードが自動的に切り替わると思い込まず、モード表示が **Autopilot** であることを確認します。

Copilot は計画に沿って実装を始め、コードを生成してテストを実行しながら作業を繰り返します。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があります。まず計画をレビューしてください。依存関係の不足やポートの競合が報告された場合は、チェック完了と見なす前にセットアップの問題を解決します。自分が起動したサーバーだけを停止してください。

## 実装をレビューして検証する

生成されたコードは、他のコードと同様にマージ前にレビューします。コードを確認し、サイトを実行して動作も確かめましょう。

1. **Changes** を開き、フィルタリングの実装とテストを調べます。
2. 複数カテゴリとパブリッシャーの組み合わせも含め、結果を Issue と承認した合意事項に照らします。変更が既存のリポジトリの指示に従っていることを確認します。
3. lint、単体テスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 実装を承認する前に失敗を解消し、該当するチェックを再実行します。Playwright の E2E 設定はビルドとプレビュー配信を行い、ローカル サーバーを再利用できます。以前のレッスンではなく、この worktree のサーバーをテストしていることを確認します。

## 新機能を試す

コードに問題がないように見えても、実際に動くか確認しましょう。前と同じようにアプリを起動し、ブラウザー キャンバスでサイトを開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザー キャンバスで開くよう Copilot に依頼します。

   ```plaintext
   Start the app and open it in the browser canvas.
   ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザー ウィンドウが開きます。
3. カテゴリを選んで結果を確認します。フィルターを解除し、次にパブリッシャーを選択して、結果が一致することを確かめます。
4. カテゴリとパブリッシャーを組み合わせ、Issue と承認済み計画に照らして結果を確認します。複数カテゴリに対応している場合は、合意した組み合わせ方を検証します。
5. 一致するゲームがない組み合わせを試し、結果がない場合の表示を確認します。フィルターを解除またはリセットして、一覧全体に戻ることも確認します。
6. 確認が終わったら、次のプロンプトを使ってセッションで起動した開発サーバーを停止します。

   ```plaintext
   Stop the dev server and close the browser canvas.
   ```

## 次のレッスンのためにセッションを維持する

まだフィルタリングの PR を作成したりマージしたりしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを維持します。次はカスタム指示をフィルタリングのコードに適用し、スキルと QA の改善を追加してから、レッスン 8 で PR を作成してマージします。開発サーバーを停止した後、セッションを終了せずに待機状態にしておき、次のレッスンで同じセッションに戻ります。
